# 评估：设备运行状态监控与进程管理

> 结论先行：**P1「心跳附带轻量指标」1–2 天即可落地，强烈建议做**（CPU/内存/磁盘/网络/IP/开机时长，客户端已具备全部通道）；GPU 与"进程重启"属 P2（各 3–5 天，前者受硬件差异拖累，后者受权限拖累）；"网页实时进程管理器"建议放弃或降级为快照式（P3）。

## 一、需求拆解与分期

| 能力 | 数据来源（Windows） | 通道 | 分期 |
| --- | --- | --- | --- |
| CPU 使用率 | `PerformanceCounter` 或 `GetSystemTimes`（免依赖） | 心跳附带 | **P1** |
| 内存/磁盘占用 | `GlobalMemoryStatusEx` / `GetDriveInfo` | 心跳附带 | **P1** |
| 网络（IP、上下行速率） | `NetworkInterface.GetAllNetworkInterfaces` | 心跳附带 | **P1** |
| 开机时长、系统版本 | `Environment.TickCount64` / WMI Win32_OperatingSystem | 心跳附带 | **P1** |
| 历史曲线 | 服务端 SQLite 存 7 天采样，折线图 | 新表 + 页面 | **P2** |
| GPU 占用/温度 | NVML（N 卡）/ Windows performance counter（通用 GPU 引擎） | 心跳附带 | P2 |
| 进程列表快照 | `Process.GetProcesses()`（含 CPU/内存） | 独立接口（心跳不该带） | P2 |
| **进程重启** | `taskkill /im xxx.exe /f` + 重启命令 | F10 指令通道扩展 | **P2** |
| 实时进程管理器（杀任意进程） | 同上 | 常驻通道 | P3，不建议 |

## 二、P1：心跳附带轻量指标（推荐，1–2 天）

### 报文设计（向后兼容）

心跳请求追加**可选** `metrics` 对象（客户端只在服务端声明 `features` 含 `metrics` 时发送，与 F10 的 `acks` 同一套协商机制）：

```json
{ "mac": "...", "secret": "...",
  "metrics": {
    "cpu_percent": 12.5, "mem_used_mb": 8192, "mem_total_mb": 16384,
    "disk_used_gb": 512, "disk_total_gb": 1024,
    "net_ip": "192.168.1.23", "net_up_kbps": 120, "net_down_kbps": 4500,
    "uptime_s": 86400, "os": "Windows 11 23H2"
  } }
```

- 大小约 200 字节，60 秒一次，对心跳契约的"轻量"原则无伤；
- 服务端只保留**最新一份**（写 `device_metrics` 表或 device 表 JSON 列），不存历史——历史曲线是 P2 的独立决定，别让心跳隐式背上存储增长；
- 网页设备卡片加一排小指标（复用 `facts` 样式），离线设备显示最后一份快照 + 时间。

### 工作量

- 客户端：MetricCollector.cs（约 150 行，全部 Win32/WMI 免依赖实现）+ 心跳请求拼装；
- 服务端：心跳处理 30 行 + 存储 60 行 + 设备卡片渲染；
- 风险点：`cpu_percent` 需要两次采样求差（客户端自己维持上次 `GetSystemTimes`），GPU/磁盘多盘时只报系统盘。

## 三、P2a：历史曲线（3–4 天，可选）

- 新表 `device_metrics_history(device_id, ts, cpu, mem, net_up, net_down)`，客户端每次心跳落一行，保留 7 天（每天一次清理任务）；
- 新接口 `GET /api/devices/{id}/metrics?hours=24` 返回降采样序列；
- 网页加一个简单折线图（不引框架，SVG 手画或引入轻量 chart 库，注意 E6 的无构建约束）；
- 风险：存储增长可控（100 台 × 1440 点/天 × 7 天 ≈ 100 万行，SQLite 无压力），但降采样和图表交互有打磨成本。

## 四、P2b：GPU 指标（3–5 天，可选）

| 硬件 | 取数方式 | 备注 |
| --- | --- | --- |
| NVIDIA | NVML（nvml.dll，驱动自带） | 最成熟，但客户端要多带一个 P/Invoke 封装，且只覆盖 N 卡 |
| 通用 | Windows 性能计数器 `GPU Engine(*)\UtilizationPercentage` | 免依赖，但只有占用率，没有温度；部分老驱动没有该计数器 |
| 温度 | LibreHardwareMonitor（开源库，~2MB） | 能读 CPU/GPU/主板温度，但依赖 WMI 内核驱动，杀软可能报敏感行为 |

建议：通用计数器做占用率，温度明确不承诺（硬件差异太大），N 卡用户可选启用 NVML。

## 五、P2c：进程列表与"进程重启"（3–5 天）

### 关键设计问题

1. **"重启进程"的语义要先定义清楚**：重启谁？由谁配置？
   - 推荐方案：**受监护进程**白名单。设备上配置"如果 xxx.exe 不在了就拉起它"（客户端本地守护，甚至不需要服务端指令）；服务端只下发"立即重启 xxx"作为补充；
   - 不推荐：网页上浏览任意进程 → 点重启。这等于把任务管理器暴露到网页，误操作面和安全面都太大。
2. **权限**：杀别人的进程需要同用户或更高权限；SYSTEM 服务装的心跳客户端（client/README 的无人值守方案）可以杀绝大多数进程，但杀 SYSTEM 进程仍受限。
3. **通道**：完全复用 F10——新增指令类型 `restart_process`，载荷 `{"name":"xxx.exe"}`；服务端指令表加一列 `payload TEXT`，其余状态机原样复用。这是 F10 架构的直接红利。

### 工作量

- 服务端：指令表加 payload 列 + 校验（进程名白名单格式）≈ 半天；
- 客户端：执行器 `taskkill /im {name} /f` + 可选拉起（需要配置可执行文件路径，配置进 config.json）≈ 1 天；
- 网页：设备编辑页加"受监护进程"配置 + 卡片按钮 ≈ 1–2 天；
- 进程列表展示：客户端随心跳带 top N 进程（CPU/内存排序前 5）≈ 半天，网页只读展示。完整的进程列表接口建议做成快照式（点"刷新"时客户端下次心跳捎带全量列表，服务端缓存 60 秒）。

## 六、不建议做的

- **网页实时进程管理器**：需要常驻双向通道 + 任意进程操作权限，安全面大、误操作代价高（杀错关键进程 = 远程变砖），收益却很低——真需要管理进程时 RDP 进去操作更稳；
- **心跳塞全量进程列表**：报文会从 200 字节膨胀到几十 KB，违背 F9 轻量契约，且 100 台设备同时上报时 SQLite 写放大明显。

## 七、工作量与优先级汇总

| 阶段 | 内容 | 估时 | 建议 |
| --- | --- | --- | --- |
| P1 | CPU/内存/磁盘/网络/IP/开机时长 快照 | 1–2 天 | **先做**，性价比最高 |
| P2b | 进程重启（受监护进程 + 指令扩展） | 3–5 天 | 有真实需求再做 |
| P2a | 7 天历史曲线 | 3–4 天 | 有排障需求再做 |
| P2c | GPU 占用（通用计数器） | 1–2 天 | N 卡 NVML 另计 |
| P3 | 实时进程管理器 | — | 不建议 |

## 八、与 F10 的关系

F10 的指令通道（排队 → 心跳捎带 → 回执）是通用的"服务端 → 客户端"控制面。本期只注册了 `shutdown` / `restart` 两个类型；P2 的 `enable_rdp`（见远程桌面评估）与 `restart_process` 都是同一状态机上新增枚举值，架构无需再动。
