# E3 接口契约（冻结）

本文件定义 F3 唤醒校验的 HTTP 接口。设备 CRUD 见 `docs/E1-contract.md`，一键唤醒见 `docs/E2-contract.md`，本文件不重复。

## 通用约定

沿用 E1/E2：成功响应直接返回对象或数组；失败响应固定为 `{"error":"<码>","message":"<中文说明>"}`。

## 状态取值（冻结）

状态是**单值**，只保留最近一次结果，没有历史、没有曲线。

| `status` | 中文 | 含义 | 是否为终态 |
| --- | --- | --- | --- |
| `pending` | 待校验 | 新建设备的默认值；服务重启后被打断的校验也回到此值 | 否 |
| `checking` | 校验中 | 轮询进行中 | 否 |
| `online` | 已上线 | 某一轮探测成功 | 是 |
| `timeout` | 超时未响应 | 等满 120 秒仍未成功 | 是 |
| `failed` | 校验失败 | 探测无法进行（命令缺失、目标配置非法） | 是 |

`pending` 与 `checking` 都是"没有结论"的状态，前端不得把它们显示成"设备离线"。

## 接口一：触发校验

```
POST /api/devices/{id}/check
```

请求体：**无**。校验目标取自设备记录的 `probe_type` 与 `probe_value`，不接受客户端传入。

响应 202：

```json
{"status": "checking", "started_at": "2026-10-18T16:30:00+08:00"}
```

字段白名单（**只允许这 2 个键**）：

| 键 | 类型 | 说明 |
| --- | --- | --- |
| `status` | string | 恒为 `"checking"` |
| `started_at` | string | 本次校验开始时间，RFC 3339 |

为什么是 202：校验是异步的，此刻还没有结论。同步等 120 秒会把 HTTP 连接拖住，也让前端无法在等待中显示进度。

### 错误码

| HTTP | `error` | 触发条件 |
| --- | --- | --- |
| 400 | `invalid_id` | 路径 ID 不是正整数 |
| 400 | `invalid_probe` | `probe_type` 为 `none`、不在 `ping`/`tcp` 之内，或 `probe_value` 为空 |
| 404 | `not_found` | 设备不存在 |
| 409 | `check_in_progress` | 该设备已在校验中，本次未启动新任务 |
| 500 | `status_write_failed` | 写入"校验中"状态失败（存储异常） |

409 是刻意的：它让"第二次点击不启动新任务"这件事**可被观测**，而不是静默返回 202 让人以为重新开始了一轮。

## 接口二：查询状态

```
GET /api/status
```

返回全部设备的状态数组，按 `device_id` 升序：

```json
[
  {"device_id": 1, "status": "online", "message": "", "checked_at": "2026-10-18T16:30:05+08:00"},
  {"device_id": 2, "status": "pending", "message": "", "checked_at": ""}
]
```

字段白名单（**每项只允许这 4 个键**）：

| 键 | 类型 | 说明 |
| --- | --- | --- |
| `device_id` | number | 设备 ID |
| `status` | string | 五个取值之一 |
| `message` | string | 归一化说明；`online` 时为空串 |
| `checked_at` | string | 最近一次**终态**的时间，RFC 3339；从未校验过为 `""` |

无数据时返回 `[]`，不返回 `null`。

### 为什么是全集而不是 `/api/devices/{id}/status`

设备上限 100，家庭自用通常不超过 10 台。列表页需要每台设备的状态，逐台查会产生 N 次请求；校验期间前端要每 2 秒刷新一次，N 次请求会被放大成 N×60 次。一个全集接口同时满足"列表显示"与"轮询等待"两个场景。

反过来，`/api/devices/{id}/status` 会多一个接口、多一套错误码，收益仅是响应体小几百字节，不划算。

### 为什么不做 SSE / WebSocket

推送能让前端少轮询，但要处理断线重连、消息序号、多标签页同步。轮询 2 秒一次、每次几百字节，在本场景完全够用。这是明确的范围取舍，不是遗漏。

## 失败原因的归一化

`message` 只允许出现下列**固定文案**，不透传系统输出：

| 场景 | `message` |
| --- | --- |
| `online` | `""` |
| `timeout` | `120 秒内未探测到设备上线` |
| 探测命令缺失 | `探测命令 ping 不存在，无法校验` |
| 目标配置非法 | `校验目标非法，请检查设备的校验设置` |
| 服务重启打断 | `服务重启，上次校验中断` |

理由：ping 的原始输出在不同系统、不同语言环境下格式不同，直接返回会让前端出现无法预期的文案，也可能泄露内网拓扑。

## 明确不做

| 不做项 | 归属 / 原因 |
| --- | --- |
| 校验历史、耗时曲线、成功率统计 | 排除清单内的"唤醒历史图表" |
| 失败自动重试整个校验流程 | 用户可再点一次；自动重试会造成重复发包与状态抖动 |
| 可配置的轮询时长与间隔 | 3-7 要求默认固定 120s/5s，本环节直接不做配置 |
| 把状态塞进 `/api/devices` 的响应 | 会破坏 E1 的 9 字段白名单，E5 已按独立资源设计 |
| 批量触发全部设备校验 | 一期排除清单内 |
