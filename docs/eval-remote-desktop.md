# 评估：远程桌面功能方案与复杂度

> 结论先行：**推荐"引导启用 RDP + 一键入口"方案**（P1，约 2–3 天），Web 内嵌桌面流（自研/WebRTC）留作 P3 长期项（约 3–6 周，风险高）。核心矛盾：远程桌面的本质是**高带宽实时视频流 + 低延迟输入回传**，与本项目"零入站端口、单 Go 容器、NAS 部署"的前提天然冲突。

## 一、候选方案对比

| 方案 | 原理 | 目标机改动 | 服务端改动 | 延迟/画质 | 安全 | 复杂度 |
| --- | --- | --- | --- | --- | --- | --- |
| **A. RDP 直连（推荐起步）** | 用系统自带 mstsc，3389 端口 | 打开 RDP 开关（脚本可代劳） | 仅提供"启用 RDP"指令 + 桌面快捷入口 | 最好（系统级） | NLA + Windows 凭据，成熟 | **低** |
| B. RDP over 隧道 | 服务端开 TCP 隧道端口转发到目标机 3389 | 同上 | Go 加一个 TCP 转发器（`io.Copy` 级别） | 好 | 封一层管理令牌认证 | **中低** |
| C. VNC / TightVNC | 目标机装 VNC 服务端，Web 端 noVNC | 安装第三方服务 | 内嵌 noVNC 静态页 + WebSocket 转 VNC | 中，帧率一般 | VNC 协议加密弱，需自己包 TLS | 中 |
| D. Rustdesk/MeshCentral 自托管 | 开源远控服务端 | 装客户端 | 再跑一个服务（可 docker） | 好 | 自成体系 | 中（多一个系统） |
| E. 自研 WebRTC 屏幕流 | 客户端抓屏 + WebRTC 推流，网页内嵌 | 升级 WolHeartbeat | Go 做 signaling + STUN/ICE | 好（可调） | DTLS 加密 | **高** |
| F. 截图轮询（伪远程桌面） | 心跳通道带 JPEG 快照 + 点击坐标回传 | 升级客户端 | 心跳报文扩展 | 差（1–5 秒一帧） | 复用现有密钥 | 低 |

## 二、推荐路线（分期）

### P1：RDP 引导 + 一键入口（约 2–3 天，建议先做）

1. 复用 F10 指令通道新增指令类型：
   - `enable_rdp` → `reg add "HKLM\SYSTEM\CurrentControlSet\Control\Terminal Server" /v fDenyTSConnections /t REG_DWORD /d 0 /f` + 防火墙放行 `netsh advfirewall firewall set rule group="远程桌面" new enable=Yes`（**需要管理员权限**——WolHeartbeat 默认非提权，需通过 UAC 提权运行一次或改用计划任务/SYSTEM 方式装客户端，见 client/README 的无人值守方案）；
   - `disable_rdp` 反向操作；
2. 网页设备卡片加「远程桌面」按钮：设备在线且 RDP 已启用 → 复制 `mstsc /v:<ip>` 提示或下载 `.rdp` 文件（服务端知道设备 IP 吗？不知道——心跳只有 MAC，需要客户端心跳附带局域网 IP，顺手就做了）；
3. 体验：浏览器点一下 → 下载 rdp → 双击进系统桌面。

优点：零自研流媒体、画质延迟都是 Windows 原生水平、凭据走 NLA。
缺点：不是"网页里看"，要跳出浏览器；需要目标机账号密码。

### P2：TCP 隧道（约 1 周，可选）

- 目标机不必暴露 3389：客户端已有的**反向连接**思路扩展为常驻 TCP 反向隧道（客户端连服务端 `GET /api/tunnel/upgrade` 升级为 hijacked TCP 流，服务端把它当成目标机 3389 的入口）；
- 服务端监听 `:13389`，管理令牌做前置认证，`io.Copy` 双向转发；
- 价值：外网/跨网段访问、目标机可以继续零入站端口。
- 复杂度点：连接生命周期管理、断线重连、并发会话、令牌过期中的连接处理。

### P3：网页内嵌桌面（3–6 周，谨慎）

- 客户端用 Windows.Graphics.Capture 抓屏 → H.264 硬编码 → WebRTC（go libdatachannel 或 Pion 数据通道发帧，输入用 DataChannel 回传）；
- 难点：Pion 集成 + NAT 穿透（局域网内用 host candidate 可绕开 STUN）、输入延迟、多显示器/DPI、剪贴板、UAC 安全桌面无法捕获、编码器兼容性；
- 结论：除非"网页内嵌"是硬需求，否则性价比远低于 P1/P2。若只是想网页看一眼状态，做 P4 监控（见另一份评估）更划算。

### 明确不推荐

- **VNC（方案 C）**：协议加密弱、还要装第三方服务，两头不占；
- **截图轮询（方案 F）**：能做"看一眼"，交互体验差，且让心跳报文膨胀一个量级，污染 F9 的轻量契约。若真需要，作为独立接口而非心跳捎带。

## 三、与现有架构的匹配度

| 现有资产 | 对远程桌面的复用 |
| --- | --- |
| F10 指令通道 | 直接下发 enable/disable_rdp（P1 零新增通道） |
| 心跳密钥 | 隧道认证可复用同一密钥体系 |
| 单容器部署 | P1/P2 不新增容器；D 才需要 |
| 客户端常驻托盘 | 隧道模式需要客户端常驻——已具备 |

## 四、工作量汇总

| 阶段 | 内容 | 估时 | 风险 |
| --- | --- | --- | --- |
| P1 | enable_rdp 指令 + 心跳带 IP + rdp 文件下载 + 卡片按钮 | 2–3 天 | 低（唯一坑：UAC 提权） |
| P2 | 反向 TCP 隧道 + 端口监听 + 认证 | 1 周 | 中（连接管理） |
| P3 | WebRTC 抓屏推流 | 3–6 周 | 高（编码/穿透/输入） |
